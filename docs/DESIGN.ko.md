# PumpDX Rebuild — 핵심 설계 v0.1

## 1. 목적과 범위

이 프로젝트는 2019년의 `DxPumpV0.76`을 새 코드베이스로 다시 만드는 작업이다. 기존 프로젝트는 레거시 참고 자료로 보존하며, 검증 없이 기존 실험 코드나 구조를 가져오지 않는다.

목표는 음악과 정확히 동기화되는 5패널 Pump It Up 스타일 리듬 게임이다. 롱노트, 곡별 BGA 영상, 브라우저 기반 채보 편집기, 1·2인용 USB 발판을 지원한다.

## 2. 설계 원칙

1. **음원이 시간의 기준이다.** 프레임 수나 노트의 화면 Y좌표로 게임 시간을 판단하지 않는다.
2. **채보는 음악 데이터다.** 고정된 16비트 문자열이 아니라 박자와 이벤트를 기록한다.
3. **화면은 계산 결과다.** 노트 위치, BGA 프레임, 이펙트는 현재 음원 시간에서 계산한다.
4. **입력은 장치와 플레이어에 귀속된다.** 여러 USB 발판을 하나의 전역 버튼 배열에 합치지 않는다.
5. **채보 제작과 게임 실행은 분리한다.** 편집기는 사람이 읽는 원본 채보를 만들고, 게임은 검증·컴파일된 채보를 읽는다.
6. **1280×720은 디자인 좌표계다.** 기존 16:9 리소스를 살리되 실제 창 크기를 고정하지 않는다.

## 3. 시간 모델

### 3.1 기준 시계

`AudioClock`은 재생 중인 음원의 위치(초)를 제공한다. 매 프레임 한 번 읽은 값이 모든 게임 로직의 기준이다.

```text
songTime = 음원 재생 시간 + 플레이어별 입력 보정값
```

`songTime`으로 다음을 처리한다.

- 입력 판정과 자동 Miss
- 일반 노트와 롱노트의 화면 위치
- 롱노트 틱
- BGA 영상 프레임
- 박자 반응형 이펙트

노트의 Y좌표를 프레임마다 누적 이동시키지 않는다. `노트 정답 시간 - 현재 음악 시간`으로 현재 위치를 매번 계산한다. 프레임이 잠깐 떨어져도 다음 프레임에서 올바른 위치로 돌아오므로 게임 시간이 누적 오차를 갖지 않는다.

### 3.2 음악 박자

원본 채보의 박 위치는 부동소수점이 아닌 정확한 분수로 보관한다. 예를 들어 3연음은 `17 + 1/3`으로 기록할 수 있고, 임의의 N연음도 같은 방식으로 표현한다.

`TimingMap`은 박 위치를 초 단위 시간으로 변환한다. 첫 버전부터 BPM 변경, 편집기 표시용 박자표 변경, 정지 구간, 곡 시작 오프셋을 지원한다.

## 4. 채보 모델

### 4.1 곡 패키지

곡 하나는 다음을 묶어 관리한다.

- 음악 파일
- 선택 사항인 BGA 영상과 정적 대체 배경
- 타이틀·배너·프리뷰 리소스
- 곡 메타데이터
- 난이도별 채보

### 4.2 노트 이벤트

레인은 `SW`, `NW`, `Center`, `NE`, `SE`의 5개다.

```text
Tap  { lane, beat }
Hold { lane, startBeat, endBeat, tickPolicy }
```

롱노트는 편집기에서 하나의 이벤트다. 화면의 몸통이나 점수용 틱을 고정된 몸통 칸 나열로 저장하지 않는다.

State 06은 다섯 레인, `TapNote`, `HoldNote`, 정렬, 검증으로 이 불변 `Chart` 계약을 구현한다. 첫 실행 가능한 `tickPolicy`는 정확한 고정 틱 수이며, 같은 시작·끝 박의 롱노트에 10틱과 100틱을 의도적으로 지정할 수 있다. 박 간격 정책은 이후 채보 컴파일러가 롱노트 이벤트의 모양을 바꾸지 않고 추가한다.

`tickPolicy`는 점수 밀도를 명시적으로 결정한다. 첫 실행 규칙은 정확한 고정 `tickCount`이며, 실행부는 이를 균등한 유지 지점으로 계산한다. 따라서 화면 길이가 같은 롱노트도 의도적으로 10개 또는 100개의 유지 콤보 이벤트를 만들 수 있다.

초기 규칙은 다음과 같다.

- 머리(시작점)는 일반 노트처럼 판정한다.
- 머리 판정 성공 후 롱노트가 활성화되며, 이미 지나가는 몸통을 밟아도 롱노트를 잡을 수 있다.
- 지정된 모든 유지 지점마다 해당 레인을 계속 밟고 있는지 검사한다.
- 너무 일찍 떼면 발을 뗀 동안 지나가는 유지 지점만 잃으며, 다시 밟으면 다음 가능한 지점부터 재개한다.
- 마지막 유지 지점은 항상 롱노트 끝 시각에 둔다.
- 화면 몸통 길이는 틱 수와 무관하게 시작·끝 박자로 그린다.

고정 `tickCount`는 머리 이후의 유지 지점 수이며 마지막 하나는 끝 지점이다. 따라서 완료한 `hold=...,10`은 머리 판정 1회와 유지 콤보 이벤트 10회를 만든다. 이로써 길이, 콤보 밀도, 끝 처리의 의미가 서로 분리된다. 재밟기 동작은 렌더링을 바꾸지 않는 게임플레이 규칙셋의 결정이다.

검증기는 끝이 시작보다 빠른 롱노트, 같은 레인의 롱노트 겹침, 그리고 같은 레인에서 롱노트의 시작부터 끝까지 포함한 구간 안에 놓인 모든 탭을 거부한다. 다른 레인은 독립적이므로 다른 패널의 탭·롱노트 동시 배치는 유효하다.

### 4.3 컴파일된 채보

브라우저 편집기는 사람이 읽을 수 있는 원본 채보를 저장한다. 컴파일러가 유효성을 검사하고, 시간순 이벤트·계산된 롱노트 틱을 가진 실행용 채보를 만든다.

기존 `.stp`는 고정 16비트 탭 채보로 가져올 수 있다. 이는 이관용 기능이며 새 포맷의 한계가 되지 않는다.

### 4.4 네이티브 원본 체보 (`.pdxchart`)

State 12는 사람이 읽고 수정할 수 있는 첫 원본 체보 계약을 도입한다. 줄 단위 형식이므로 전용 바이너리 도구 없이도 사람과 향후 브라우저 맵툴 모두가 만들 수 있다.

```text
schemaVersion=1
id=example-single
[tempo]
0=142
[notes]
tap=SW,1/3
hold=C,4,12,10
hold=SE,17+1/3,25+1/3,100
```

`SW`, `NW`, `C`, `NE`, `SE`는 다섯 발판을 뜻한다. 박은 정수·분수·대분수 표기로 정확하게 기록한다. 롱노트 하나는 시작, 끝, 원하는 정확한 틱 수 하나만 가지므로 시각 길이와 콤보 밀도는 독립적이다. 네이티브 로더는 잘못된 데이터, 레인, 불가능한 롱노트, 순서가 맞지 않는 BPM 구간을 게임플레이와 같은 불변 `Chart` 검증기로 거부한다. `.stp`는 탭 전용 이관 형식으로 유지하며, 카탈로그는 확장자로 로더를 선택한다.

## 5. 판정·점수·게이지

### 5.1 판정 방식

입력이 들어오면 `JudgementEngine`은 해당 플레이어·레인의 아직 처리되지 않은 가장 이른 후보 노트를 찾는다.

```text
timingError = 입력 시간 - 노트 정답 시간
```

절댓값을 규칙셋의 시간 구간과 비교한다. 세로 슬라이스의 초기값은 조정 가능하다.

| 결과 | 최대 절대 오차 |
| --- | ---: |
| Perfect | 22 ms |
| Great | 45 ms |
| Good | 90 ms |
| Bad | 135 ms |
| Miss | Miss 구간 이후 |

너무 이른 입력은 노트를 소비하지 않는다. Miss 기한을 넘긴 노트는 자동으로 Miss가 된다. 스크롤 속도는 화면 거리만 바꾸며 판정 구간은 바꾸지 않는다.

### 5.2 점수와 콤보

`ScoreState`는 플레이어별로 존재한다. Perfect~Miss 횟수, 점수, 현재 콤보, 최대 콤보, 롱노트 틱을 기록한다. 구체적인 점수 표는 씬 코드에 박아 넣지 않고 교체 가능한 규칙셋으로 관리한다.

### 5.3 에너지 게이지

`LifeGauge`는 `0.0`~`1.0`의 게임 모델이며 렌더러와 분리한다. 판정 결과가 설정 가능한 증감값을 적용한다. 0일 때의 스테이지 실패 여부도 플레이 모드/규칙셋이 결정한다.

렌더러는 둥근 마스크 채움, 색상 구간, 부드러운 추적, 충전·피격 플래시, 위험 상태 펄스를 표현한다. 셰이더는 마스크와 그라데이션에만 쓰고 체력 규칙을 담지 않는다.

## 6. 씬과 수명 관리

기존의 SongMenu 내부 Game/Result 구조를 다음의 독립 씬으로 바꾼다.

```text
Boot/Loading → MainMenu → SongSelect → Gameplay → Result → SongSelect
                    ↘ Settings / DeviceAssignment
```

- `SongSelect`은 곡·채보·속도·모드·플레이어 배정을 담은 불변 `PlaySession`을 만든다.
- `GameplayScene`은 음원, 채보 런타임, 판정, 활성 노트 뷰, BGA, 점수, 게이지를 소유한다.
- 플레이 종료 시 `ResultData`만 생성하고 전환 후 `GameplayScene`은 해제한다.
- `ResultScene`은 `ResultData`만 표시하며 살아 있는 게임 객체를 잡고 있지 않는다.
- 곡 리소스는 공유 캐시에 남길 수 있으므로 올바른 씬 분리가 불필요한 재로딩을 뜻하지 않는다.

## 7. 렌더링과 BGA

논리 UI 캔버스는 1280×720이다. 실제 출력은 비율을 유지해 확대하며, 필요하면 레터박스를 사용한다.

State 04의 기반은 Direct3D 11 배경 위에 그리는 범용 Direct2D/DirectWrite 씬 오버레이다. 씬은 의미 기반 `headline`, `detail`, `instruction` 문자열만 제공하고, framework 렌더러는 1280×720 논리 변환만 적용하며 씬 규칙을 알지 않는다. 이 텍스트 오버레이는 개발 중 화면 구조를 검증하기 위한 표현층이며, 이후 단계에서 테마가 해석한 UI 리소스와 애니메이션으로 교체한다.

State 07은 첫 게임 필드 투영을 더한다. 5개 레인, 리셉터, 탭 헤드, 롱노트 몸통은 채보 초 단위 시간과 현재 곡 시계 초 단위 시간으로부터 계산한다. State 08은 같은 단조 `DebugSongClock`으로 규칙을 검증한다. 입력 엣지는 오직 `입력 시간 - 노트 시간`으로 비교하며, 최종 판정 창 이후 자동 Miss가 나고, 렌더링 좌표를 다시 읽어 판정하지 않는다. 기본 개발 판정 창은 Perfect ≤30 ms, Great ≤60 ms, Good ≤100 ms, Bad ≤150 ms다. State 09에서 FMOD 기반 `AudioClock`이 이 어댑터를 교체하되 판정 엔진은 바꾸지 않는다.

State 09는 `FmodAudioPlayer`와 `FmodSongClock`으로 이 교체를 구현한다. 곡 매니페스트는 안정적인 곡 id, 화면 표시 메타데이터, 원래 음원 파일명, 밀리초 단위 오프셋을 소유하며 C++ 코드가 파일명에서 제목을 추측하지 않는다. 음원은 Git에서 제외한 `assets/local/` 아래에 두고 매니페스트만 버전 관리한다. FMOD SDK 경로는 로컬 CMake 설정이며, 실행 DLL은 로컬 빌드 때만 실행 파일 옆으로 복사된다.

State 10은 원본 파일을 수정하지 않고 레거시 5레인 `.stp` 탭 채보를 가져온다. 첫 레인의 고정 16비트 격자에서 `1` 하나는 `TapNote` 하나가 된다. importer는 예전 로더의 호환 규칙도 의도적으로 보존한다. 헤더 칸 수는 첫 레인 길이보다 하나 클 수 있고, 첫 레인 길이를 넘는 다른 레인의 끝 기호는 무시한다. 예전 `startPoint`는 오디오 장치 오프셋이 아니다. 이는 Y 좌표였으며, 예전 45픽셀 격자, `3×BPM` 노트 속도, Y=83 판정선을 기준으로 `(startPoint - 83) / 180` 박의 채보 리드인으로 변환한다. 점수 판정은 0–100 기본 에너지를 갱신하며, FMOD 재생이 끝나면 점수·최대 콤보·클리어/실패 상태를 가진 Result로 세션이 넘어간다.

State 11은 곡 매니페스트에 정적 BGA 경로를 더한다. `SceneOverlayRenderer`는 게임플레이 중에만 WIC로 이미지를 불러오며, 파일이 없거나 읽을 수 없으면 세션을 실패시키지 않고 어두운 코드 생성 대체 배경을 유지한다. 같은 필드에는 0–100의 단순 세로 에너지 게이지도 추가한다. 이는 의도적으로 기본 표현 어댑터에 그친다. 영상 BGA, 동적인 씬 애니메이션, 스킨형 게이지 이펙트는 분리된 단계 3 시스템으로 남긴다.

State 12는 롱노트 작성을 구조만이 아니라 실제로 실행할 수 있게 만든다. `.pdxchart`는 정확한 N연음 박, BPM 변경, 탭, 서로 다른 고정 틱 수의 롱노트를 불러온다. 다만 이 단계에서는 라이브 롱노트 점수를 아직 활성화하지 않는다. State 13에서 해결된 롱노트 헤드·틱·끝 타임라인을 실제 플레이에 연결한다.

State 13은 이 롱노트를 실제 게임플레이에 연결한다. 성공한 머리는 레인별 롱노트 상태를 시작하며, 이미 지나가는 몸통을 밟으면 다음 가능한 유지 지점부터 롱노트를 잡는다. 끝 지점을 포함해 균등 분배한 유지 지점은 `HoldTick` 또는 `HoldEnd` 판정 이벤트를 낸다. 점수·콤보·게이지·결과 요약은 탭과 같은 방식으로 이 이벤트를 받으며, `ScoreState`는 유지 지점 총수도 별도로 기록한다. 롱노트를 떼면 발을 뗀 동안 지난 지점만 Miss가 되고, 다시 밟으면 다음 지점부터 재개하지만 이미 지난 지점을 되살리지는 않는다. 이 PIU식 재밟기 규칙은 렌더링과 타이밍을 섞지 않고도 명확하게 테스트할 수 있다.

State 14는 로컬 `NewSongToGod` 음원에서 사용할 버전 관리 네이티브 롱노트 오버레이를 추가한다. 현재 매니페스트는 여전히 수정하지 않은 `NewSongToGod_10.stp`를 불러온 뒤, 오버레이에 담긴 독자적인 롱노트 이벤트만 실행 체보에 합친다. 따라서 F5에서는 레거시 탭 흐름을 유지하면서 짧고 긴 롱노트, 8/12/16/20개의 유지 지점 밀도, 서로 다른 패널의 동시 롱노트를 확인할 수 있다. Direct2D 임시 필드는 잡은 롱노트 몸통을 활성 팔레트 색으로 구분한다. 최종 노트 스킨, 버스트 이펙트, 애니메이션은 채보 규칙이 아닌 이후 테마 작업으로 남긴다.

State 15는 실제 레거시 탭 흐름을 확인한 뒤 레인 계약을 강화한다. 탭은 롱노트 머리부터 끝까지 같은 레인을 공유할 수 없다. `NewSongToGod` 오버레이는 각 레거시 레인에서 측정한 빈 구간 안에만 배치하고, 다른 레인끼리는 자유롭게 겹칠 수 있다. 이로써 화면·게임플레이의 관례가 작성자의 주의에만 맡겨지지 않고, 결정적인 체보 검증 오류가 된다.

State 16은 개발용 임시 필드 배치를 고정된 1280×720 1인용 게임플레이 레이아웃으로 교체한다. `GameplayLayout`은 체보 투영과 Direct2D 렌더링이 공유하는 단일 기준이다. 중앙 5레인 필드는 X=290–990, 판정판은 Y=498, 필드 클립 범위는 Y=156–672이다. 가로형 에너지 바는 필드 바로 위에, 곡 정보와 점수는 상단 밴드에, 판정·콤보 피드백은 판정판 위 중앙에 둔다. HUD는 렌더러에 게임 규칙을 넣지 않고 점수·콤보·최대 콤보·롱노트 유지 틱 수를 전달한다. 리셉터는 누르는 동안 밝아지고, 미활성 롱노트는 차분하게, 잡은 롱노트는 활성색으로, 유지 틱을 놓친 롱노트는 주황/빨간 경고 테두리로 표시한다. 이는 의미를 전달하는 임시 시각 요소이며, 최종 화살표·스킨·파티클·전환 애니메이션은 이후 테마 기반 작업으로 남긴다.

State 16-1은 PIU식으로 소비되는 롱노트 몸통 표현을 더한다. 활성 롱노트를 실제로 밟고 있고 머리가 판정판을 지났다면, 렌더러는 지난 머리를 숨기고 몸통 시작점을 판정판에 고정한다. 따라서 아직 지나지 않은 꼬리만 남아 화면의 롱노트 길이가 계속 줄어든다. 한 번도 잡지 못한 롱노트는 판정판 위로 정상 진행시켜 놓친 구간이 보이게 한다. 끝 유지 지점을 밟아 성공하면 롱노트는 즉시 필드에서 제거된다. 이 화면 동작은 게임플레이 상태와 오디오 시간만으로 계산하며 판정 결과 자체를 바꾸지 않는다.

State 16-1-1은 소비된 몸통 해제 처리의 불변 조건을 정한다. 한 번 롱노트를 잡아 머리·몸통 일부가 판정판을 지났다면, 이후 발을 떼어도 그 소비된 구간은 다시 나타나지 않는다. 아직 소비되지 않은 꼬리의 개별 이동은 이후 State 16-1-2에서 정한다.

State 16-1-2는 해제 뒤의 화면 동작을 완성한다. 발을 떼는 순간 남은 꼬리는 판정판에서 시작해 정상 스크롤 속도로 위로 계속 이동하며, 뒤이어 지나는 유지 지점마다 Miss를 낸다. 이동하는 것은 남은 구간뿐이며, 이미 소비된 과거 구간은 복구하지 않는다. 다시 밟으면 그 시점에 남은 꼬리가 다시 판정판에 붙어 유지한다. 마지막 유지 지점을 놓친 경우도 끝이 판정판을 지난 뒤 자연스럽게 필드 밖으로 나간다.

State 16-1-3은 끝난 롱노트의 시각 수명을 닫는다. 레인 입력으로 판정판에 붙일 수 있는 대상은 아직 처리하지 않은 유지 지점이 하나 이상 남아 있고 끝 시각에 도달하지 않은, 이미 잡은 롱노트뿐이다. 모든 유지 지점이 처리된 뒤 같은 레인을 다시 눌러도 판정판에 롱노트 잔상이 재생성되면 안 된다. 이 규칙으로 이후의 독립된 입력이 지나간 롱노트의 시각 잔상을 만들지 않는다.

State 16-3은 임시 둥근 사각형 노트·판정판을 방향성을 가진 5패널 심볼로 교체한다. 왼쪽부터 레인 계약은 `SW`, `NW`, `Center`, `NE`, `SE`로 고정한다. 네 모서리 패널은 대응하는 대각 화살표를 그리고, 중앙 패널은 구별되는 네 방향 심볼을 그린다. 같은 심볼을 판정판과 이동 노트 머리에 모두 사용하므로, 화면 레인·키보드 연결·향후 실제 발판 배정이 하나의 명확한 시각 정체성을 공유한다. 이 기반 단계의 심볼은 자체 소유 Direct2D 벡터 도형으로 그리며, 이후 테마 시스템이 의미 기반 노트/판정판 슬롯으로 교체해도 레인 의미와 타이밍은 바꾸지 않는다.

State 17은 점수 규칙을 바꾸지 않고 필드가 입력에 반응하게 만든다. 모든 판정 이벤트는 레인·판정 품질·음원 시계 시작 시간을 가진 고정 용량 `GameplayEffectPool`로 들어간다. 이 풀을 현재 음원 시간으로 읽으면 렌더러 전용 `GameplayFeedback` 스냅샷이 만들어진다. 스냅샷에는 해당 판정판의 짧은 성공 플래시 또는 붉은 Miss 플래시, 시간이 지나며 사라지는 판정 버스트, 성공 콤보 숫자 확대, 성공/실패에 따른 게이지 광택이 들어간다. 효과는 0.30초 후 만료되고 슬롯을 재사용하므로 계속 플레이해도 시각 객체를 새로 할당하거나 오래된 효과를 남기지 않는다. 렌더러는 이 스냅샷만 받아서 그리고 점수 상태나 노트를 직접 판정하지 않는다. 이후 테마의 파티클·스프라이트 이펙트는 같은 인터페이스 뒤의 벡터 표현만 교체한다. BGA 영상은 디코더·미디어 시간·대체 배경 규칙이 이 피드백 경로에 영향을 주지 않도록 별도 다음 State로 남긴다.

State 18은 곡이 소유하는 첫 BGA 영상 어댑터를 추가한다. 선택 사항인 매니페스트 `videoBgaPath`는 곡 매니페스트 기준 상대 경로로 해석하며 로컬 미디어만 가리킨다. `MediaFoundationBgaPlayer`는 RGB32 프레임으로 디코딩하도록 설정한 Media Foundation Source Reader를 사용한다. 프레임 요청은 노트와 판정이 사용하는 FMOD/음원 시계의 초 단위를 그대로 받고, 해당 시각 이하의 프레임까지 진행하면서 이미 늦은 디코딩 프레임은 버린다. 따라서 오디오나 게임 진행을 늦추지 않는다. 의미 있는 뒤로 이동이 생기면 리더를 seek한 뒤 가장 가까운 키 프레임부터 다시 진행한다. 현재 시각에 맞는 가장 최신 프레임은 일련번호가 바뀔 때만 Direct2D 게임 배경으로 업로드한다. 영상 파일이 없거나 읽을 수 없거나 지원하지 않거나 아직 디코딩되지 않았으면 기존 `staticBgaPath` 이미지를 계속 사용하며, 영상 실패 때문에 세션이 끝나서는 안 된다. 현재 로컬 곡에는 영상 경로를 넣지 않았으므로, 소유자가 로컬 영상을 제공할 때까지 의도적으로 이 정적 대체 경로를 사용한다.

State 19는 재사용 가능한 UI 전용 `SceneTimeline`을 도입한다. 씬에 들어갈 때마다 독립적인 steady clock 타임라인을 다시 시작하고, 헤드라인 등장·반복 펄스·시간차를 둔 상세 정보 공개·시간차를 둔 안내 문구 공개 값을 만든다. 이 타임라인은 음원 시계를 읽거나 바꾸지 않으므로 메뉴와 결과 화면의 움직임이 노트 타이밍에 영향을 줄 수 없다. 메인 메뉴에는 로고 옆에서 숨 쉬는 듯한 빛을, 선곡 화면에는 맥동하는 선택 밴드를, 결과 화면에는 맥동하는 결과 구분선을 추가하며 세 화면은 같은 카드/텍스트 순차 등장 효과를 공유한다. 이는 이후 테마 이미지·스프라이트 레이어가 교체할 의도적인 벡터 임시 표현이지, 미래 씬 아트를 코드에 고정하는 방식이 아니다.

State 16-2는 사용자가 제공한 Pump It Up 인게임 레퍼런스를 기준으로 1인 HUD를 다시 배치한다. 좁은 5레인 필드는 왼쪽 X=162–734에 두고, 판정판은 Y=152까지 올린다. 노트는 아래 필드에서 이 상단 판정판으로 올라간다. 가로형 에너지 바는 그 위 X=188–680 / Y=20–46에 맞춘다. 판정 텍스트는 판정판 바로 아래, 콤보는 그 아래에 배치하고, 곡 정보와 점수는 오른쪽 상단으로 이동해 주변 BGA가 읽히는 영역을 남긴다. 이는 가운데 넓은 필드와 낮은 판정판을 사용하던 State 16 배치를 대체하지만, 동일한 `GameplayLayout` 시간·렌더링 계약은 유지한다.

게임 화면의 렌더링 순서는 다음과 같다.

```text
BGA 영상/정적 배경 → 가독성 오버레이 → 노트 필드 → 리셉터·발판 효과
→ 판정·콤보 효과 → 플레이어별 HUD → 전환 오버레이
```

BGA 영상도 `AudioClock`을 기준으로 재생한다. 디코딩이 늦으면 영상 프레임을 건너뛰고, 음원과 게임 진행을 절대 늦추지 않는다. 영상을 재생할 수 없으면 정적 대체 배경으로 플레이한다.

싱글은 5패널 필드를 중앙에 두고, 2인 모드는 공통 BGA 위에 좌우 P1/P2 필드와 HUD를 따로 둔다.

### 7.1 씬 UI 모션

BGA 외에도 각 화면은 `SceneTimeline`을 갖는다. 스프라이트 프레임 시퀀스, 위치·크기·회전·투명도 트윈, 이징, 시간 콜백을 재사용한다. 개별 씬 코드에서 이미지를 제각각 로드하지 않고 아틀라스와 애니메이션 정의를 사용한다.

두 시계는 의도적으로 분리한다.

- **게임/박자 시계:** 노트 효과, 리셉터, 콤보 펄스, 박자 반응형 인게임 연출은 `AudioClock`을 따른다.
- **UI 시계:** 메뉴 배경, 선택 커서, 패널 전환, 버튼 상태, 결과 숫자 등장 등은 일반 UI 시간을 따른다.

초기 장면 연출 방향은 다음과 같다.

- `MainMenu`: 배경 루프, 로고 등장, 버튼 호버·선택·확정 상태
- `SongSelect`: 배너 슬라이드, 선택곡 포커스, 난이도 커서, 확정/취소 전환
- `Gameplay`: 발판 점등, 리셉터 반응, 판정 폭발, 콤보 펄스, 게이지 피드백, BGA 위 HUD 강조
- `Result`: 판정 수치 순차 등장, 등급 공개, 복귀 안내
- `DeviceAssignment/Settings`: 장치 카드, 입력 테스트 플래시, 배정 확인

전환 중에는 애니메이션을 안전하게 중단 또는 완료할 수 있어야 한다. 모션 감소 설정에서는 비필수 연출을 단순화한다.

## 8. 입력과 플레이어

각 실제 컨트롤러는 독립된 `InputDevice`와 버튼 상태를 가진다. 장치 입력은 전역으로 합치지 않는다.

`DeviceAssignmentScene`은 P1로 쓸 실제 발판의 가운데를 밟게 한 뒤 P2에도 같은 절차를 요청한다. 장치 경로/GUID가 안정적이면 저장한다. 완전히 동일하면서 고유 시리얼이 없는 발판은 재연결 후 재배정이 필요할 수 있으며, 프로그램이 물리적 좌우 위치를 자동으로 알아낼 수는 없다.

데이터 모델은 다음 모드를 수용한다.

- 싱글: 1인·5패널
- 대전: P1/P2 각각 5패널과 독립 점수
- 협동: 두 장치의 입력을 하나의 플레이 세션에 연결
- 향후 더블: 한 플레이어가 두 장치·10패널 사용

입력 지연 보정, 키 설정, 입력 테스트, 재연결, 키보드 대체 입력은 게임플레이 코드가 아니라 설정/장치 배정 화면에서 다룬다.

## 9. 런타임 성능

- 곡 시작 전 채보 전체와 필요한 리소스를 로드한다.
- 화면 진입 시간 범위의 노트만 활성화된 렌더 뷰를 가진다.
- `NoteViewPool`은 끝난 일반/롱노트 뷰를 재사용한다.
- `EffectPool`은 판정·콤보·발판·파티클 효과를 재사용한다.
- 매 프레임 활성 객체만 갱신·렌더링한다.
- 채보 데이터는 불변이며 플레이 도중에는 게임 상태만 바뀐다.

이는 기존의 선로딩 장점은 유지하면서도 모든 노트 객체를 끝까지 갱신하던 구조를 피한다.

## 10. 브라우저 채보 편집기

편집기는 게임 런타임 씬이 아니라 별도의 브라우저 앱이다. 마디/박자 기반 타임라인에서 다음을 지원한다.

- 마디나 선택 단위의 스냅: 4, 8, 12, 16, 24, 32, 임의 N, 스냅 없음
- 분수 박 위치를 통한 3연음·N연음
- BPM/박자표 표시
- 탭 배치, 드래그 롱노트 생성·길이 변경·틱 정책 설정
- 음원 프리뷰, 파형, 메트로놈, 스크롤/확대
- 실행 취소/다시 실행, 복사/붙여넣기, 검증, 내보내기/컴파일
- 레거시 고정 그리드 `.stp` 가져오기

`stepCreator2.html`은 유용한 프로토타입 참조로 보존한다. 하지만 58마디·마디당 16행의 고정 표를 만들고 5개의 `0`/`1` 문자열만 내보내므로, 새 시간·롱노트 모델에는 사용하지 않는다.

State 21은 `tools/chart-editor/`에 로컬 구현 기반을 만든다. 채보 파싱·직렬화는 React/Canvas 화면과 분리하며, 런타임과 호환되는 `.pdxchart` 텍스트를 열고 저장한다. 노트마다 DOM 요소를 만들지 않고 하나의 Canvas 타임라인에 그리며, 기본 탭 편집은 되돌리기 가능한 문서 스냅샷으로 기록한다. 지원 브라우저에서는 File System Access API로 열었던 파일에 바로 저장하고, 지원하지 않으면 같은 형식의 파일을 내려받는다. 롱노트 작성·임의 그리드·N연음·파형은 다음 State에서 추가한다.

State 22는 편집기를 의도한 세로 5레인 형태로 바꾼다. 음악 시간은 아래로 진행하고 각 레인은 고정된 열을 유지한다. 비어 있는 같은 레인 구간에서 아래 방향으로 드래그해 롱노트를 만들며, 선택한 롱노트의 아래쪽 꼬리를 드래그해 길이를 바꾼다. 틱 수는 롱노트마다 명시적으로 편집한다. 새 롱노트나 변경한 롱노트가 같은 레인의 다른 이벤트와 겹치면 편집기가 막아 런타임의 충돌 없는 채보 규칙을 지킨다.

State 23은 레거시 이관을 단방향·검증 가능하게 만든다. `LegacyStpConverter`는 런타임과 같은 리드인 계산으로 수정하지 않은 원본 `.stp`를 읽고, 필요하면 기존 네이티브 롱노트 오버레이를 합쳐 완전한 `Chart`를 만든다. 이어서 `NativeChartWriter`가 정확한 분수 박·레인·BPM 구간·탭·롱노트 틱 수를 `.pdxchart`로 쓴다. 변환 왕복 테스트는 출력 파일을 다시 읽어 이벤트 종류, 레인, 시작/끝 박, 롱노트 틱 수를 비교한다. 원본 `.stp`는 `assets/local/charts/legacy/`에서 그대로 보존하고, 완전한 변환본은 Git에서 제외되는 `assets/local/charts/converted/`에 둔다.

## 11. 첫 플레이 가능 버전의 완료 조건

테스트 곡 하나에서 아래가 모두 되면 첫 구현 단계가 완료다.

1. 1280×720 논리 레이아웃이 창 크기와 전체 화면에서 올바르게 확장된다.
2. 로딩 완료 후 음원이 시작하며, 그 시간이 게임의 유일한 기준이다.
3. 싱글 플레이어가 여러 스크롤 속도에서 탭 노트를 플레이해도 판정 시간창이 달라지지 않는다.
4. 노트·입력·Miss·콤보·점수·`ResultScene`이 정의된 시간 모델을 사용한다.
5. 정적 BGA 대체 배경이 동작하며, 이후 영상 BGA를 붙여도 게임 타이밍은 바뀌지 않는다.
6. 박→시간 변환과 판정 경계에 자동 테스트가 있다.

롱노트, 영상 BGA, 2인 장치 배정, 편집기는 이 수직 슬라이스 위에 차례로 추가한다.

## 12. 확정된 런타임 기술

런타임은 Windows 네이티브 C++20 스택을 사용한다. 초기 프로젝트는 CMake와 Direct3D 11로 만들고, 이후 단계에서 음악 재생에는 FMOD, BGA 영상에는 Media Foundation, Windows 컨트롤러 경계에는 Raw Input/DirectInput을 추가한다. 이렇게 하면 기존 프로젝트의 네이티브 C++ 성격은 이어 가되 Direct3D 9 시대의 구조는 가져오지 않는다.

Direct3D 11과 CMake는 골격 단계부터 사용한다. FMOD, 영상 재생, 실제 발판 지원은 각각 필요한 단계에서만 추가해 첫 빌드의 외부 의존성을 작고 검증 가능하게 유지한다.

## 13. 객체와 파일 구조

새 프로젝트는 의도적으로 여러 파일과 책임 중심 구조를 사용한다. 단지 파일 크기를 줄이기 위해 나누지는 않지만, 어떤 씬·장치·게임플레이 객체도 모든 일을 떠안는 관리자 객체가 되어서는 안 된다. 네이티브 C++ 프로젝트를 선택할 경우의 초기 구조는 다음과 같다.

```text
PumpDX_Rebuild/
├─ docs/                         # 설계와 사용자용 기술 문서
├─ assets/                       # 버전 관리하는 개발용 리소스, C++ 소스 아님
├─ src/
│  ├─ framework/                 # 재사용 가능한 기술 기반, PumpDX 규칙 미포함
│  │  ├─ render/                 # 렌더러, 뷰포트, 스프라이트, 영상 표면
│  │  ├─ audio/                  # AudioClock, MusicPlayer, 음원 리소스 로딩
│  │  ├─ input/                  # 장치, 키 설정, Raw Input/DirectInput 경계
│  │  ├─ assets/                 # ResourceCache, 매니페스트, 테마 패키지 로딩
│  │  └─ platform/windows/       # 창과 Windows 전용 어댑터
│  └─ game/                      # PumpDX 고유 규칙과 화면 표현
│     ├─ application/            # PumpDX 시작 처리와 게임 흐름 조립
│     ├─ chart/                  # 채보 모델, TimingMap, 컴파일러, 유효성 검사
│     ├─ content/                # 곡 메타데이터와 카탈로그
│     ├─ gameplay/               # JudgementEngine, ScoreState, LifeGauge, 노트 런타임
│     ├─ scenes/                 # 씬별 폴더와 해당 씬 전용 표현 객체
│     │  ├─ main_menu/
│     │  ├─ song_select/
│     │  ├─ gameplay/
│     │  ├─ result/
│     │  └─ device_assignment/
│     ├─ session/                # PlaySession과 불변 ResultData
│     └─ ui/                     # 레이아웃, SceneTimeline, UI 애니메이션
├─ tools/                         # 별도 브라우저 채보/테마 편집기 프로젝트
└─ tests/                         # 실행 단위 테스트 데이터와 테스트 도구
```

`src/framework`는 기존 프로젝트에서 유효했던 분리를 계승한 1급 경계다. 재사용 가능한 플랫폼·기술 서비스를 소유하고, `src/game`은 PumpDX 고유 규칙·채보 의미·씬 표현을 소유한다. 게임은 framework 인터페이스를 사용할 수 있지만, framework 코드는 PumpDX 게임 규칙에 의존하지 않는다. 상태와 수명을 갖는 공개 C++ 객체는 보통 자신의 헤더/소스 쌍을 가진다. 예를 들어 `JudgementEngine.hpp`와 `JudgementEngine.cpp`처럼 둔다. 작고 분리할 수 없는 값 타입은 `JudgementTypes.hpp`처럼 함께 둘 수 있으며, 구현 전용 보조 함수는 해당 `.cpp`에 숨긴다.

객체의 책임 경계는 다음처럼 고정한다.

- `GameApplication`은 서비스 시작과 루프만 소유하며 게임 규칙을 담지 않는다.
- `SceneManager`는 현재 씬과 전환만 관리하며 점수나 실제 장치 상태를 소유하지 않는다.
- `GameplayScene`은 플레이 세션의 객체를 조립하지만 판정·점수·게이지·BGA·HUD·노트 뷰는 각각의 객체에 맡긴다.
- `JudgementEngine`은 시간 판정만 결정하고, `ScoreState`와 `LifeGauge`는 판정 결과를 각각 반영한다.
- `TimingMap`만 음악 박/초 변환을 담당하며 렌더 코드가 BPM 계산을 다시 구현하지 않는다.
- `PadDevice`는 실제 컨트롤러 하나를 소유하고, 플레이어 배정은 장치 입력을 섞지 않은 채 연결한다.
- `ResourceCache`와 `ThemeManifest`가 리소스를 찾으며 씬에는 리소스 경로를 하드코딩하지 않는다.

의존성은 안쪽으로 흐른다. 플랫폼·렌더·오디오 어댑터는 좁은 인터페이스를 통해 게임플레이와 씬에서 사용할 수 있지만, 핵심 채보·판정 규칙은 창·텍스처·씬에 의존하지 않는다. 전역 싱글턴 관리자나 모든 기능을 담는 `GameManager`는 사용하지 않는다. 이 원칙이 테스트와 추후 영상/입력/렌더 백엔드 교체를 현실적으로 만든다.

새 기능을 추가할 때는 어느 도메인이 소유하는지 먼저 정하고, 무관한 클래스에 코드를 붙이지 않는다. 관찰 가능한 로직이 있는 새 소스 파일에는 가장 작은 관련 테스트 또는 테스트 데이터를 함께 추가한다.

## 14. 스킨·테마 시스템

게임의 시각 리소스는 버전이 있는 테마 패키지로 교체할 수 있게 만든다. 테마는 게임의 표현만 바꾸며, 채보 시간·판정 규칙·입력 배정·게임플레이 레이아웃 계약 자체를 바꾸지 않는다.

```text
themes/<theme-id>/
├─ theme.json                     # 스키마 버전, 메타데이터, 슬롯 연결 정보
├─ menu/                          # 배경, 로고, 버튼, 선택 UI
├─ gameplay/                      # 노트, 롱노트 몸통, 리셉터, 발판 점등, HUD
├─ judgement/                     # 판정, 콤보, 이펙트 스프라이트 시트
├─ result/                        # 결과 배경, 등급, 숫자 스킨
├─ settings/                      # 장치 배정·설정 화면 이미지
└─ fallback/                      # 선택 사항인 BGA/정적 대체 표현
```

`theme.json`은 `gameplay.note.sw`, `ui.song_select.cursor`, `result.grade.a`처럼 변하지 않는 의미 기반 키를 실제 파일과 표현 메타데이터에 연결한다. 메타데이터에는 논리 디자인 크기, 기준점/피벗, 스프라이트 시트 격자 또는 프레임 영역, 애니메이션 시간·반복, 필요할 경우 9-slice 정보, 기본 색상/투명도를 담는다. 코드는 의미 키만 사용하고, 각 씬에서 테마 파일 경로를 직접 참조하지 않는다.

State 05는 이 계약의 첫 실행 가능한 부분을 제공한다. 선택한 `theme.json`에서 스키마 버전, 테마 id, 오버레이용 다섯 색상, `resources.<의미-키>` 연결을 읽는다. `ResourceCache`는 선택된 테마 패키지 안의 상대 경로만 해석하며, 패키지 밖으로 나가는 경로는 거부한다. 스프라이트 메타데이터·이미지 디코딩·핫 리로드는 별도 시스템이 아니라 이후에 같은 스키마로 확장한다.

렌더러는 이미지 크기와 별개로 게임플레이 기하 구조를 유지한다. 노트 이미지를 바꿔도 판정 위치는 움직이면 안 된다. 노트/리셉터의 기준점은 레이아웃 계약에 두고, 테마는 시각 피벗과 오프셋만 제공한다. 테마 검증기는 필수 키, 파일 읽기, 프레임 영역, 지원하는 이미지/영상 형식, 1280×720 논리 크기 호환성을 검사한다. 선택 리소스가 없으면 현재 기본 테마를 대신 사용하고, 필수 리소스가 없으면 명확한 오류와 함께 테마 적용을 막는다.

`ThemeManifest`와 `ResourceCache`는 씬/플레이 세션 전환 지점에서 선택된 테마를 불러온다. 개발 빌드는 매니페스트나 이미지 변경을 안전하게 핫 리로드할 수 있고, 배포판은 준비된 패키지를 사용한다. BGA는 기본적으로 곡이 소유하며, 테마는 정적 대체 배경이나 시각 오버레이를 제공할 수 있다.

향후 브라우저 `Theme Editor`는 같은 매니페스트를 편집하며, 다음을 단계적으로 지원한다.

1. 슬롯 단위 이미지 교체, 미리보기, 크기/크롭, 기준점, 색상, 투명도 조절
2. 스프라이트 시트 분할과 UI/이펙트 애니메이션 정의
3. 씬별 실시간 미리보기, 검증, 패키지 가져오기/내보내기/복제, 테스트 테마 적용

테마 패키지는 스키마 버전과 게임 버전 호환 범위를 가진다. 패키지에는 제작자가 소유하거나 배포 권한을 가진 리소스만 포함한다.

## 15. 곡 카탈로그와 Song Select

런타임은 `assets/catalog/`의 버전 관리 대상 `*.song.manifest`를 모두 읽는다. 같은 안정적인 `id`를 가진 항목은 하나의 곡이며, 각 매니페스트가 선택 가능한 난이도 하나를 뜻한다. 화면 제목·아티스트 정보는 로컬 음원/채보 경로와 분리하므로 제목과 파일명이 같을 필요가 없다.

Song Select는 1280×720 논리 좌표에서 기존 구조를 유지한다. 큰 선택 곡 배너, 작은 이전/다음 배너, 하단 현재 곡 배너, 좌측 플레이어/상태 패널, 별도 난이도 패널로 구성한다. 곡/난이도 인덱스는 런타임 상태가 소유하고, 렌더러에는 읽기 전용 화면 스냅샷만 전달한다.

현재 키보드 조작은 5패널 메뉴 흐름을 따른다. 곡 탐색 중에는 `Z`/`C`로 이전/다음 곡을 고르고, `S`로 난이도 선택에 들어간다. 난이도 선택 중에는 `Z`/`C`로 난이도를 이동하고 `S`로 시작한다. `Q`/`E` 또는 Escape는 난이도 선택을 나가며, Enter는 데스크톱 확인을 위한 즉시 시작 단축키로 남긴다. 실제 발판도 이후 같은 의미의 조작으로 연결한다.

임시 레거시 호환 기능으로, 곡 탐색 중 `Q → E → Q → E → S`를 입력하면 배속이 x1.0에서 x3.5까지 0.5씩 증가하고 다시 x1.0으로 순환한다. 이 입력은 일반 Song Select 조작보다 먼저 소비되며 좌측 상태 패널에 표시된다. 시작한 게임에는 노트의 화면 이동 속도만 전달하고, 음원 시계와 판정 시간창은 바꾸지 않는다.

원래 메뉴의 곡은 공개 저장소와 분리해 로컬 전용으로 복원한다: Africa(16), Flying Dock(3/5), New Song To God(10), You Are Good(14). MP3/STP 원본은 무시되는 `assets/local/`에 두며, 공개 커밋에는 매니페스트와 문서만 남긴다. 따라서 새 클론은 안전하고, 현재 개발 폴더에서는 바로 플레이할 수 있다.
